# LLM 的上下文（Context）—— 学习包

## 1. 学习目标

完成本资料后，你应当能够：

1. **能用自己的话解释** 什么是 LLM 的"上下文窗口"（Context Window）以及它和"Token"的关系
2. **能估算出** 一个 128K token 的窗口大致能装多少中文 / 英文
3. **能区分** 5 种常见的 context window 优化技术（压缩 / 分块 / 去重 / 摘要 / 优先级）
4. **能判断** 什么时候该用 RAG 检索代替"把全文塞进 context"
5. **能诊断** 一个 LLM 应用"答非所问"的常见根因是不是 context 被截断

---

## 2. 核心问题

1. **是什么**：Context Window 是什么？为什么用 token 计数而不是字数？
2. **为什么**：为什么 LLM 有 context 上限，而不是可以无限长？
3. **怎么做**：超出 context 怎么办？5 种主流优化技术各自适用什么场景？
4. **何时不用**：是不是"窗口越大越好"？有什么反直觉的副作用？
5. **怎么评估**：怎么判断你的应用"被 context 限制"了？

## 3. 结构化解释

### 3.1 前置知识

- 知道 LLM 是基于"前面所有 token"预测下一个 token 的模型
- 知道"Transformer"是当前主流 LLM 的底层架构
- 知道一次 LLM 调用（inference）会**同时**消耗输入 + 输出 token

### 3.2 核心定义

> **Context Window（上下文窗口）= LLM 在一次推理中能"看见"的最大 token 数**。包括 system prompt、对话历史、工具结果、用户输入和模型输出本身 [1]。

关键点：
- **以 token 计，不是字数**。100 token ≈ 75 英文单词 ≈ 50–100 个汉字 [1][2]
- **输入和输出共享同一份预算**。输出 5000 token 意味着窗口里输入只能放更少
- **超出窗口的默认行为是"悄悄截断"**，不是报错 [1]

### 3.3 关键机制：为什么有上限

三大技术约束（按 LlamaIndex [1] 和 Redis 博客的总结）：

1. **自注意力的 O(n²) 复杂度**：每个 token 要和所有其他 token 比对，token 数翻倍，计算量变 4 倍
2. **KV Cache 内存增长**：推理时 GPU 显存里要缓存所有历史 token 的 Key/Value
3. **GPU 内存带宽瓶颈**：自注意力计算要不断在 SRAM（快但小）和 HBM（慢但大）之间搬数据

> **我的理解（原创类比）**：
> 把 context window 想成"图书管理员的桌面"——
> - LLM 推理时，**所有要用的书都要摊在桌面上**
> - 桌面越大（context 越长），**摊开 + 翻阅的耗时越长**（O(n²)）
> - GPU 显存就是桌子，桌子物理大小有上限
> - 早期桌面只够摊 4K token 的"参考书"，现在最好的能摊 1M–10M

### 3.4 形式化：5 种优化技术

LlamaIndex 总结的 5 种核心技术 [1]：

| 技术 | 做什么 | 适用场景 | Token 节省潜力 | 实现复杂度 |
|------|--------|---------|----------------|------------|
| **Prompt 压缩** | 把啰嗦的 system prompt 改简洁 | system prompt 冗长 / 重复 | 中（15–40%） | 低 |
| **分块（Chunking）** | 长文档切成段，只喂最相关段 | 文档超过窗口（如 OCR、长 PDF） | 高 | 中 |
| **去重** | 删掉重复指令、模板套话 | prompt 慢慢长出冗余 | 低–中 | 低 |
| **摘要** | 把多轮历史先摘要再喂 | 长多轮对话 | 高（10–20%） | 中 |
| **优先级排序** | 关键信息放最近 / 离 query 最近 | 窗口快满了 | 不定 | 低 |

> 这些技术**不互斥**。生产环境的成熟系统通常**组合使用** —— 先分块、再压缩、最后按优先级喂入 [1]。

### 3.5 反直觉：窗口越大 ≠ 越好

- **Lost-in-the-Middle 效应**：研究显示 LLM 对 context **中间**段的信息关注度比开头 / 结尾低
- **成本线性增长**：输入 token 计费，1M 窗口的请求成本是 128K 的 8 倍
- **延迟增加**：长 context 推理时间显著拉长
- **误导风险**：塞太多无关信息，模型反而"分心"

## 4. 应用案例

### 案例 1：长 PDF 问答（正面）

- **场景**：用户上传一份 200 页的产品手册 PDF，问"第 137 页的保修条款是什么？"
- **天真做法**：把整个 PDF 塞进 context，祈祷模型能定位 ❌
- **正确做法**（LlamaIndex 推荐的 4 步组合 [1]）：
  1. **Chunk** PDF 成 512 token 的段
  2. **Embedding** 向量化后建索引
  3. 用户提问时**检索**最相关的 Top-K 个段（这就是 RAG）
  4. **只把 Top-K 段 + 用户问题**喂给 LLM
- **结果**：在 128K 窗口下也能精确回答，成本降一个量级

### 案例 2（反面 / 踩坑）：Chatbot 突然"失忆"

- **症状**：用户和客服 Chatbot 聊到第 20 轮，AI 突然"忘了"用户在第 3 轮说的关键信息（"我女儿对花生过敏"）
- **常见根因**：
  - 平台用的是 8K 窗口
  - 第 3 轮的内容在第 10 轮左右被**静默截断**（不是报错）
  - 模型真的看不见了，但 UI 没提示
- **错误诊断**：以为是 LLM 质量问题 ❌
- **正确诊断**：是 context 窗口满了，**LlamaIndex 明确指出"oldest content is silently truncated"** [1]
- **修复**：
  - 升级到 128K+ 窗口
  - 或：每 10 轮做一次"摘要 + 重新喂入"
  - 或：把关键事实（花生过敏）**显式提前到 system prompt** 保留
- **来源**：Rhesis 文档明确"Loss of continuity"是 context 超限的常见症状 [2]

## 5. 概念辨析

### 5.1 Context Window vs Memory

| 维度 | Context Window | Memory |
|------|----------------|--------|
| 范围 | 一次推理内 | 跨推理（跨会话） |
| 存储位置 | GPU 显存（临时） | 外部存储（持久） |
| 容量 | 受模型架构限制 | 几乎无限 |
| 典型实现 | 直接拼到 prompt | 长期向量库 + 摘要 |
| 关系 | Memory 通过检索/摘要**喂入** Context | Context 是 Memory 的"工作面" |

> 关键洞见：**没有 Context Window 再大都不够装下"全部 Memory"**。Memory 系统本质是"在有限 Context 里塞进最相关的历史"。

### 5.2 Token vs 字符 vs 汉字

| 单位 | 1 token 大致对应 | 备注 |
|------|------------------|------|
| 英文单词 | 1 token ≈ 0.75 词 | [1] |
| 英文字符 | 1 token ≈ 4 字符 | 含空格、标点 |
| 汉字 | 1 token ≈ 1.5–2 字 | 中文 token 化更细碎 |
| 代码 | 1 token ≈ 3–5 字符 | 符号多，密度高 |

> 这就是为什么"一份 100K 中文字文档"听起来不大，但实际可能要 150K–200K token。

### 5.3 RAG vs 塞全文

| 维度 | 塞全文（Context Stuffing） | RAG（检索增强） |
|------|---------------------------|----------------|
| 适用文档量 | 小于窗口 | 远大于窗口 |
| 检索 | 无 | 有（语义/关键词） |
| 成本 | 高（每次都付全量 token） | 低（只付检索到的 Top-K） |
| 实时性 | 弱（要重新索引才能更新） | 强（索引更新即可） |
| 失败模式 | 越界截断 | 检索不到相关内容 |

> **判断准则**：文档 / 知识库**小于窗口**且**很少变** → 塞全文；否则 → 上 RAG。

## 6. 自测题

<details>
<summary><strong>题 1（理解）</strong></summary>

**问题**：用一句话解释什么是 LLM 的 context window？

**答案**：LLM 一次推理能"看见"的最大 token 数，包含输入 + 输出。

**解析**：关键是"看见"和"一次推理"。很多新手以为"我之前说过的话 LLM 都记得"——其实超过窗口就被悄悄截断。
</details>

<details>
<summary><strong>题 2（应用）</strong></summary>

**问题**：你的应用窗口是 128K token，用户上传了一本 200K token 的英文书。**最简单的修正方法是什么？**

**答案**：用 RAG 检索 Top-K 段喂入，而不是把整本书塞进 context。LlamaIndex 推荐 4 步：分块 → 索引 → 检索 → Top-K + query 喂入 [1]。

**解析**：这是个常见面试题。正确答案不是"升级到 200K 窗口"，而是"不要把所有内容都装进 context"——这是 5 种优化技术的核心思想。
</details>

<details>
<summary><strong>题 3（分析）</strong></summary>

**问题**：客服 Chatbot 聊到第 15 轮突然忘了用户在第 3 轮说的关键事实。**最可能的根因是什么？**

**答案**：context window 满了，第 3 轮内容被静默截断。Rhesis 文档明确这是 context 超限的典型症状 [2]。

**解析**：不是模型质量问题，是工程问题。修复方法：升级窗口 / 加摘要 / 把关键事实前置到 system prompt。
</details>

<details>
<summary><strong>题 4（评价）</strong></summary>

**问题**：有人说"以后 context 窗口会无限大，就不用 RAG 了"。**你怎么反驳？**

**答案**（三个反驳点）：
1. **成本**：1M 窗口的输入 token 成本是 128K 的 8 倍，文档量再大就贵得用不起
2. **Lost-in-the-Middle**：研究显示 LLM 对中间段关注度低，**窗口大反而更容易"分心"**
3. **延迟**：长 context 推理显著变慢，交互体验差
所以 RAG / 检索 / 摘要不会被淘汰，反而和长窗口**互补**。

**解析**：这是考察"对 context 理解的深度"。死记"窗口越大越好"是错的，要看成本 / 质量 / 延迟三方面。
</details>

<details>
<summary><strong>题 5（应用）</strong></summary>

**问题**：现在有一个 system prompt 重复了 3 次同样的指令（"你是 X，请做 Y"）。**用 LlamaIndex 5 种优化技术中的哪一种修？**

**答案**：**去重（Removing Redundancy）**。LlamaIndex 明确这是低复杂度 / 中等收益的技术 [1]。

**解析**：5 种技术不要混用。这是去重，**不是**压缩（压缩是改写简化），**不是**分块（分块是处理长文档），**不是**摘要（摘要是处理历史）。
</details>

<details>
<summary><strong>题 6（创造）</strong></summary>

**问题**：设计一个系统：用户上传 1000 份简历，HR 问"有 5 年 Python 经验 + 做过推荐系统的候选人有哪些？"请用"分块 + 检索 + Top-K"思路描述。

**答案要点**（开放题）：
1. 把每份简历 chunk（比如按"工作经历 / 项目 / 技能"段分）
2. 每段 embedding 向量化，建向量索引
3. HR 问句 embedding → 检索 Top-K 段（比如 Top 50）
4. 把 Top 50 段 + HR 问题一起喂给 LLM
5. LLM 输出候选人名单 + 引用（哪份简历的哪段）

**解析**：这是个 mini 系统设计题。考察"你能不能把抽象的 RAG 思路落到具体工作流"。
</details>
